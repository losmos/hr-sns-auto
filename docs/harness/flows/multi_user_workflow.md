# 멀티 유저 워크플로우

이 문서는 여러 개발자가 각자 브랜치에서 하네스 문서를 갱신할 때 따르는 규칙을 설명한다. git 사용법 일반론이 아니라 하네스 문서에 특화된 규칙만 다룬다.

## 문제 정의

- 여러 개발자가 브랜치에서 각자 `PROJECT_CONTEXT.md`와 `HANDOFF.md`를 갱신하면 병합 시 충돌이 생긴다.
- 하네스 문서는 성격에 따라 병합 가능성이 다르므로, 문서별로 다른 규칙을 적용한다.

## 문서별 병합 특성

| 문서 | 갱신 방식 | 병합 특성 |
| --- | --- | --- |
| `PROJECT_CONTEXT.md` | 추가 중심 (결정, 확정 사실이 누적된다) | 병합 친화적 |
| `HANDOFF.md` | 덮어쓰기 중심 (매 작업이 전체를 다시 쓴다) | 병합 불가 |

## PROJECT_CONTEXT 규칙

- 결정(DEC)은 충돌 불가능한 `DEC-YYYYMMDD-<slug>` ID를 사용한다. 순번 ID와 달리 두 브랜치가 동시에 결정을 추가해도 같은 ID가 생기지 않는다.
- 추가는 해당 섹션 말미 append를 관례로 한다. 서로 다른 브랜치의 추가가 같은 줄을 두고 다투는 경우를 줄인다.
- 두 브랜치의 결정이나 확정 사실이 내용상 상충하면 도구가 아니라 팀 합의로 푼다. 병합 도구는 텍스트 충돌만 해결할 수 있고 의미 충돌은 해결하지 못한다.

## HANDOFF 규칙

- 브랜치 병합 시 `HANDOFF.md`를 3-way merge하지 않는다. 서로 다른 작업의 직전 기억을 줄 단위로 섞으면 어느 쪽도 아닌 상태가 된다.
- 병합자가 병합 시점의 실제 상태를 기준으로 `HANDOFF.md`를 새로 작성한다.
- 브랜치 `HANDOFF.md`에서 장기 가치가 있는 내용은 병합 전에 판별 테스트(시간 테스트, 영향 테스트)를 적용해 `PROJECT_CONTEXT.md`로 승격한다. 승격하지 않은 내용은 브랜치 기록으로만 남는다.

## 개발자별 복사 문서를 만들지 않는 이유

- `HANDOFF.<이름>.md` 같은 개발자별 복사 문서를 만들지 않는다.
- 복사 문서가 생기면 단일한 현재 상태가 사라진다. 기억 없는 에이전트가 작업 시작 시 어느 문서를 읽어야 할지 판단할 기준이 없어지고, 문서 간 상충이 누적된다.

## 완화 관례

- 하네스 문서를 갱신하는 브랜치는 짧게 유지한다. 브랜치 수명이 짧을수록 병합 시점에 새로 쓸 `HANDOFF.md`의 간극이 작다.
- 오래 가는 브랜치는 `HANDOFF.md` 갱신을 병합 직전으로 미룬다. 중간 상태를 반복해서 기록해도 병합 시점에 다시 쓰이므로 낭비가 된다.
